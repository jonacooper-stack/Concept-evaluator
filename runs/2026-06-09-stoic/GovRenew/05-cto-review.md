CTO REVIEW — GovRenew

ONE-PARAGRAPH TECHNICAL READ
GovRenew is technically modest and that is its strength: the software layer is a deadline-tracking calendar, a document-assembly workflow, a records archive, and a read-only ingestion pipeline off the SAM.gov public Entity API to discover prospects and monitor expiration dates. None of that is a research problem — boring CRUD, scheduled jobs, document templating, a notification engine, assemblable on an off-the-shelf stack in ~6–9 dev-weeks to a revenue-earning MVP. The catch the one-pager names is right: the value-creating work — the actual SAM renewal, SBA 8(a)/HUBZone/WOSB/SDVOSB recertifications, entity validation — is largely manual portal work with no public write API, so the software is genuinely a monitoring/assembly/audit layer wrapped around an irreducibly human compliance-specialist service. This de-risks the build (no fragile government write integrations) but caps how much "software leverage" the founders can honestly claim, and makes the named GovCon specialist's labor — not code — the throughput constraint.

ARCHITECTURE SKETCH
- Frontend: a thin client portal (Next.js on Vercel, or Remix) — onboarding, credential dashboard, deadline timeline, document upload/download, renewal status. Low complexity.
- Backend: standard app server (Node/TS or Python/FastAPI) on a managed host (Render/Fly/App Runner) with Postgres (Supabase/RDS) as system of record. Small data model: entities, credentials, deadlines, renewal cases, documents, audit events.
- Scheduler / async: the real "engine" — a cron/queue worker (pg-cron, or a managed scheduler + a worker on SQS/Inngest/Trigger.dev) that polls SAM.gov Entity API on a cadence, recomputes expiration windows, fires tiered alerts (90/60/30/7-day) by email/SMS (Postmark/SendGrid + Twilio).
- Integrations: SAM.gov Entity Management / Get Opportunities public APIs (READ ONLY — entity lookup, registration status, expiration date) via an api.data.gov / SAM system account key; SBA DSBS / certification directory data (read, partly scrape-or-CSV). No government WRITE API exists, so submissions are manual through SAM.gov and certify.SBA.gov by the specialist.
- Document assembly: templated PDF/docx (docx-templates, Carbone, or a headless engine) to pre-fill recert packages and rep-and-cert worksheets. Medium complexity, well-trodden.
- Records archive: object storage (S3) with versioning + lifecycle, encrypted at rest, mapped to each credential for SBA-examination / size-protest evidentiary trails.
- Auth/hosting: off-the-shelf auth (Clerk/Auth0/Supabase Auth) with MFA, RBAC; one cloud region. ML/AI: optional and non-critical — an LLM can draft narrative attestations and summarize SBA guidance, nothing load-bearing. Real complexity hides in (a) keeping the SAM.gov read-API ingestion reliable as the government changes endpoints/throttles, and (b) the human-workflow state machine tracking a half-finished portal submission the software cannot execute.

BUILD PLAN TO REVENUE-EARNING MVP
~6–9 dev-weeks of one developer to a paying MVP; first dollar can arrive before the software is fully built, because delivery is human-led and software is back-office leverage.
1. Credential data model + client portal CRUD (deadlines, credentials, document upload, case status) — ~2.5 wks. Core; not punt-able.
2. SAM.gov read-API ingestion + deadline/expiration monitor + tiered alert engine — ~2 wks. The differentiated wedge; not punt-able.
3. Records archive on encrypted S3 with versioning + per-credential evidence trail — ~1 wk. Core for "audit-ready."
4. Document-assembly templates for the top 2–3 credential types (SAM renewal worksheet, one SBA recert package) — ~1.5 wks. Start with SAM + one set-aside; punt the long tail.
5. Prospect-list generation from SAM/DSBS read data (expiration-date sorting) — ~1 wk. Could be a throwaway script / manual CSV at first; punt the polished version.
Punt to v2: LLM attestation drafting, multi-state vendor-registration automation, billing tiers beyond a single Stripe plan, a customer-facing API. The MVP that earns revenue is items 1–3 plus a manual specialist doing the submissions.

INFORMATION SECURITY POSTURE
Sensitive but not extreme data: business entity identifiers (UEI, CAGE, EIN/TIN), ownership and eligibility attestations, owner PII (SDVOSB veteran status, WOSB/8(a) ownership — potentially SSNs or VA documentation), and possibly delegated government-portal access. Threat model: a breach exposes TINs, ownership structures, and worst case stored portal credentials — a PII incident and a fraud-enablement risk. Controls at launch (not later): TLS + at-rest encryption (S3/Postgres KMS), a real secrets manager (never credentials in env files), MFA on all accounts, RBAC least-privilege, full audit logging of who touched which document (doubles as the audit-trail product feature), versioned backed-up object storage. The biggest security decision is portal access: storing customer SAM/SBA passwords is a liability to avoid — pursue legitimate delegated-administrator roles where permitted; if shared credentials are unavoidable, isolate them in a vault with break-glass + tight rotation. Documented retention/deletion + breach-notification plan from day one. SOC 2 Type II is attainable and the founders have run SOC 2 cycles (per profile) — a genuine asset; not required for an SMB GovCon customer to sign, but a sales accelerant upmarket. Basic written IR + logging/alerting + a test-restored encrypted backup, all inside the build window.

AVERAGE SCORE: 7.5 / 10

TOP 3 TECHNICAL STRENGTHS
- The build is deliberately small and boring: a CRUD portal, one scheduled monitoring worker, document templates, an encrypted archive — ~6–9 dev-weeks on a fully off-the-shelf stack, with revenue reachable before the software is finished.
- By avoiding any government WRITE integration and keeping submissions manual, the architecture sidesteps the single most fragile dependency it could have had; nothing load-bearing rides on an unstable government endpoint.
- The compliance-heavy data plays to a founder strength (real SOC 2 Type II / HIPAA / GDPR operating experience), so the security posture and eventual SOC 2 sales asset are bridgeable in-house.

TOP 3 TECHNICAL RISKS
- Portal-credential / delegated-access model: operating SAM.gov and certify.SBA.gov on a customer's behalf may require storing or sharing government login credentials — a serious PII/fraud liability and possible ToS problem if not solved via legitimate delegated-administrator roles.
- Throughput is human, not software: submission cannot be automated, so scaling revenue means scaling specialist headcount; the "software-leveraged" claim is partly real (monitoring/assembly/archive) and partly a managed-service labor business software only assists.
- Government API drift: api.data.gov / SAM endpoint or schema changes can silently break monitoring and the prospect-list engine, requiring an adapter rebuild and risking missed deadlines — the exact failure the product promises to prevent.

BIGGEST SINGLE RISK
The gap between the product promise ("we keep your registrations current and never-lapsed") and the irreducible manual reality that submissions happen through government portals the software cannot drive. Two coupled hazards. First, the access model: to truly "keep it current" the firm must either hold delegated administrator roles (where SAM/SBA permit a third-party administrator) or store/share customer portal credentials — and credential storage is precisely the high-blast-radius secret (a government login that can alter a contractor's federal eligibility record) that turns an ordinary breach into a fraud event and a reputational catastrophe in a trust-sensitive market. Second, the deadline-miss liability: the core promise is no registration lapses, but execution depends on a human specialist completing a manual portal workflow on time; if a SAM API schema change silently breaks the alert engine, or a specialist is overloaded, a customer's registration lapses, they lose award eligibility, and GovRenew owns a direct, contractually-attractive damages claim. Both are manageable — delegated roles + a hardened vault for the first; schema-tolerant ingestion with redundant manual date-entry and clear SLA/limitation-of-liability terms for the second — but must be designed in before scale, not after the first lapse.

QUESTIONS THE FOUNDERS MUST ANSWER BEFORE I'M COMFORTABLE
- Exactly how will you access customers' SAM.gov and certify.SBA.gov accounts — via a permitted delegated/third-party administrator role, or by holding their credentials? If the latter, what vaulting/rotation/break-glass controls protect them, and does it violate the portals' terms of use?
- What is the verified human throughput per specialist — how many account-renewals and SBA recertifications per year — since that, not the software, sets the revenue ceiling and unit economics?
- Have you confirmed the api.data.gov / SAM Entity API exposes per-entity expiration/registration status at a rate limit sufficient to monitor your whole book daily, and what is the fallback if it is deprecated/throttled mid-operation?
- What contractual limitation of liability and SLA language will you carry, given a missed deadline directly costs the customer award eligibility and creates a damages claim?

RECOMMENDATION: GO
From a purely technical/security standpoint this is a clean, low-risk build: a thin off-the-shelf SaaS wedge (portal + monitoring scheduler + encrypted archive + document templates) achievable in ~6–9 dev-weeks, with the most fragile possible dependency — a government write integration — deliberately designed out by keeping submissions manual. The architecture scales trivially on managed Postgres and S3; the genuine ceiling is human specialist throughput, an operating/staffing question for other council members, not a re-architecture risk. The two things to resolve before scale are both solvable and must be designed in from day one: the portal-access/credential model (pursue legitimate delegated-administrator roles; never casually store government passwords) and schema-tolerant ingestion with redundant manual date-entry plus contractual liability caps to absorb the deadline-miss exposure. Solve those up front and the technology side is feasible, well-scoped, and not hiding bombs.
