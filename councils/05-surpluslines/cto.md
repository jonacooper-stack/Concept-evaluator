CTO REVIEW — Managed Surplus-Lines Tax, Stamping & Diligence Compliance for E&S Brokers

ONE-PARAGRAPH TECHNICAL READ
One of the more tractable compliance-managed-service concepts, because the hard part is not the software but the encoded rule set, and that rule set is finite, public, and slow-changing. The architecture is a boring, well-understood stack: a data-ingestion pipeline, a rules/tax-calculation engine, a document/form generator, a deadline scheduler, and a records vault — none a research problem, all buildable incrementally while a human specialist carries the early filings manually. The genuine technical risk is not "can we build a CRUD app" (we can) but the long-tail integration reality: ~50 state surplus-lines tax surfaces and ~15 stamping-office portals each have idiosyncratic formats, some with APIs/bulk upload and many without, so a meaningful fraction of "filing" stays semi-manual portal entry for a long time — fine for a managed service (human in the loop by design) but caps the "fully automated" story. The fundable revenue-earning MVP is a thin slice (2–4 high-volume states, CSV ingest, tax calc, return generation, deadline tracking) that the specialist files behind, not a 50-state automation platform.

ARCHITECTURE SKETCH
- Frontend: thin Next.js client on Vercel — broker uploads a CSV/AMS export, sees policies, allocations, computed tax, upcoming deadlines, downloadable/filed returns. Internal-tool-grade workspace.
- Backend: single Postgres-backed service (Node/TS or Python/FastAPI) on a managed host. Core objects: brokerage, policy, premium-allocation, jurisdiction-rule, filing, deadline, document.
- The wedge — tax & allocation rules engine: a versioned, effective-dated rules table (state, line, tax rate, base, stamping fee, filing cadence, deadline formula, home-state allocation method). Data + a deterministic calculator, NOT ML. Effective-dating is the single most important design decision (reproduce what was correct on the filing date during an audit years later).
- Form/return generation: deterministic templating — PDF generation (templating engine + PDF library, or fillable AcroForms per state) and structured exports in each stamping office's required upload format (CSV/XML/fixed-width). Grind, not difficulty.
- Integrations: stamping-office portals (FSLSO, SLTX, CA SLA SLIP, IL SLA) — a few offer bulk-upload/API; most are manual portal sessions. Optional inbound AMS (AMS360, Applied Epic, EZLynx) — start with CSV export, not deep API, to avoid platform lock.
- Async/background: a scheduler (BullMQ/Sidekiq/Temporal) driving the deadline calendar, reminders, filing-status state machine. This plus effective-dated rules is where real correctness work lives.
- Records vault: document storage (S3 + SSE) for affidavits, filed returns, confirmations — the audit-defense artifact; append-only/immutability semantics matter.
- ML/AI: optional and bounded — LLM-assisted parsing of messy AMS exports/affidavit extraction + content marketing. The money math must be deterministic rules, NOT an LLM; any plan putting an LLM on the tax-calc critical path is wrong and I'd reject it.
- Auth/hosting: off-the-shelf (Clerk/Auth0/WorkOS); nothing exotic.

BUILD PLAN TO REVENUE-EARNING MVP
~8–12 dev-weeks of one developer for a 2–4-high-volume-state MVP, assuming the specialist handles actual portal submission and exceptions from day one (software needn't file autonomously to earn the first dollar).
1. Data model + CSV ingest + brokerage/policy workspace (~2 wks). Punt deep AMS API to v2.
2. Rules engine for the first 2–4 states (TX, FL, CA + one non-stamping) — effective-dated rates, bases, stamping fees, allocation method, deadline formulas (~3–4 wks). The wedge; correctness over breadth. Each additional state is incremental content work thereafter, not new architecture.
3. Return/stamping-export generation + records vault for affidavits/confirmations (~2–3 wks). Generate the artifact; specialist files manually at first.
4. Deadline scheduler + status dashboard + reminders (~1–2 wks). The retention engine.
5. Auth, billing (Stripe + setup invoicing), basic audit logging (~1 wk, mostly off-the-shelf).
Punt to v2: deep AMS integrations, automated portal submission via APIs/RPA, broad 50-state coverage, LLM affidavit extraction, SOC 2 formalization.

CRITICAL ASSUMPTIONS
1. The rule set is finite, public, reproducible. ASSUMED true, largely verifiable — DOI/DOR sites and ~15 stamping offices publish rates/bases/cadences/formats. Verify: fully encode 3 states (one stamping, one non-stamping, one multi-state-heavy like CA) end-to-end in a week and have the specialist confirm outputs match hand-filing.
2. Multi-state premium allocation is rule-based, not judgment-based. ASSUMED [70–90% rule-based]. Post-NRRA the home state generally governs, but some apportionment is interpretive. Verify on 10 real multi-state policies: what fraction needed human judgment? A large share → less software leverage → more consulting.
3. Stamping/DOR filing surfaces tolerate the workflow. ASSUMED — many are manual portals, no API. Verify: list, for the top 6 states, API/bulk-upload vs interactive-portal-only. Determines how much filing stays human labor.
4. CSV/AMS exports are clean enough to ingest. ASSUMED [moderate risk] — real broker data is messy. Verify with 3 real anonymized exports before building the ingest. Messy data adds onboarding labor per customer (relevant to whether the $2K–$10K setup fee is real margin).
5. A single named specialist can credibly carry early filings across states without a per-state credential. ASSUMED — filing is under the broker's surplus-lines license; the service prepares returns the broker remits. Verify legal posture (a technical-scope dependency: if per-state licensure is required to file on behalf of brokers, the ops model changes).

INFORMATION SECURITY POSTURE
Data: policy and premium data (commercially sensitive, sometimes insured names/risk details), broker license/identifiers, and crucially the filed tax returns and diligent-search affidavits (financial/regulatory records the broker must defend in an audit). Sensitive business data + some PII (insured names/addresses), but not regulated-PHI or payment-rails by default — and the design deliberately does NOT take custody of tax funds (broker remits from own trust account), removing the single largest security/liability surface a fintech version would carry. A genuinely smart scoping decision, credited. Threat model: (a) data breach exposing brokers' premium books/insured data; (b) integrity failure — a corrupted/incorrect filing or lost audit record, a business-ending reputational event; (c) availability around hard deadlines — an outage on a filing-deadline day is materially worse here than for most SaaS; (d) credential handling — if you ever automate portal submission you'll store brokers' stamping-office logins, a high-value secret store. Controls at launch (off-the-shelf): TLS; encryption at rest (RDS/S3 SSE + KMS); a real secrets manager; SSO/MFA; RBAC; append-only audit logging on every filing artifact; automated encrypted backups with tested restore; immutable/versioned records vault to reproduce a filed return exactly during audit. ~1–2 dev-weeks if chosen from day one vs a painful retrofit. At scale: SOC 2 Type II becomes a sales asset (founders' SOC 2 background makes it bridgeable); IR runbook, key rotation, and (if RPA added) a hardened credential vault threat-modeled before building.

AVERAGE SCORE: 7.5 / 10

TOP 3 TECHNICAL STRENGTHS
- The hard part is content, not architecture: a deterministic, effective-dated rules engine over a finite, public rule set means no research risk and a clean ~5-component system buildable in ~8–12 dev-weeks.
- Deliberately no custody of tax funds — broker remits from its own trust account — removes the single largest security/regulatory-liability surface a fintech version would carry; a sign the founders scoped this thoughtfully.
- The proprietary, accreting asset (encoded multi-state rules corpus + append-only filing/audit history) is both a real moat and a clean, owned, portable data architecture.

TOP 3 TECHNICAL RISKS
- Long-tail integration drag: ~50 tax surfaces + ~15 stamping portals, many with no API and only manual entry, mean a meaningful fraction of "filing" stays human labor indefinitely — fine for a managed service but caps the automation/GM narrative; must not be oversold as a platform.
- Multi-state allocation judgment-share: if apportionment needs frequent human interpretation rather than deterministic formulas, software leverage drops and the model tilts toward staffed consulting.
- Integrity/correctness is existential: the whole value prop is audit-cleanliness, so a single class of systematic calculation or deadline-tracking bug can directly cause a customer penalty or license action — reputationally fatal, demanding golden-file regression tests per state most MVPs skip.

BIGGEST SINGLE RISK
The gap between the "software-leveraged platform" framing and the reality that, across ~50 state tax surfaces + ~15 stamping offices, much of the actual filing and a non-trivial slice of multi-state allocation stays human-in-the-loop for a long time. Not a build-breaker — it's sold as a managed service with a specialist in the loop, so a human filing into a portal is by design — but it determines whether this is a high-margin software business with a thin services wrapper, or a staffing-heavy services business with software assist. The difference shows up directly in the ladder: the former scales to ~$500K+/founder by adding brokerages against fixed software; the latter scales by adding specialist headcount, throttling margin and the founders' own leverage. Mitigation: verify, before heavy building, how much of the top-6-state workload is deterministic-and-automatable vs inherently manual, and architect so every manual step is a candidate for incremental automation (bulk-upload formats first, RPA/API last) rather than baking permanent human labor into the unit economics.

QUESTIONS THE FOUNDERS MUST ANSWER BEFORE I'M COMFORTABLE
- For the top 6 target states (TX, FL, CA, NY, IL, AZ), which stamping offices/DORs offer bulk-upload or API filing, and which are interactive-portal-only? Determines how much of "filing" is software vs permanent human labor — and therefore your gross margin and the realism of the ladder.
- On 10–20 real multi-state policies, what fraction of premium allocations are deterministic vs requiring a specialist's judgment? Separates a scalable rules-engine product from a consulting business with software assist.
- What is your golden-file test and rules-update process — how do you guarantee a filed return is correct and reproducible-on-audit years later when rates change, and who owns continuously re-encoding rate/deadline/format changes across states?

RECOMMENDATION: GO
A technically sound, low-research-risk, capital-light build with a thin defensible custom wedge and a smart no-fund-custody scoping decision that removes the worst liability surface. One developer can ship a revenue-earning 2–4-state managed-service MVP in ~8–12 dev-weeks with the specialist filing behind the software, and the architecture scales to hundreds of brokerages on one Postgres instance without rewrite. The two things that keep it from a higher score are operational, not architectural: the permanent rules-maintenance burden and the human-labor share of actual filing/allocation, both of which bound the margin and ladder math rather than feasibility. Verify the three questions (especially the per-state filing-surface and allocation-judgment audits) with the named specialist before committing to broad state coverage, build golden-file regression tests per state from day one given the existential cost of a correctness bug, and design the security controls in from the start where they cost ~1–2 dev-weeks rather than a painful retrofit.
