CTO REVIEW — Rampart (AI-first CMMC compliance platform for the DIB)

ONE-PARAGRAPH TECHNICAL READ

This is a buildable, off-the-shelf-heavy SaaS with one genuinely hard custom component: an LLM pipeline that ingests a contractor's messy source documents and produces control-mapped policy/SSP artifacts and a 110-control gap scorecard against NIST SP 800-171. That document-generation wedge is feasible today with retrieval-augmented generation over a fixed, well-bounded control catalog (Claude/GPT-4-class models + an embeddings store), and that is exactly the bet the founders are making. The technical trap is not the build — a competent solo dev can ship a revenue-earning Phase 1 in roughly 8-12 dev-weeks — it is the information-security and compliance-posture bar: a platform whose explicit job is to hold a defense contractor's CUI-adjacent compliance evidence and connect to their identity/endpoint/cloud tenants is itself a high-value, high-scrutiny target, and "we'll harden it later" is disqualifying in this niche. The realistic CTO read is GO on feasibility, with the caveat that the security/architecture work is front-loaded, not deferrable, and the Phase 2 integrations are a second, larger engineering project that should be punted out of the MVP.

ARCHITECTURE SKETCH

- Frontend: a standard Next.js/React single-page app (document upload, guided interview, gap scorecard dashboard, task/POA&M views, evidence library, exports). Vercel or a single container host. No exotic UI; the complexity is in workflow state, not pixels. [~2 dev-weeks for the v1 surface.]
- Backend/API: a single typed backend (Next.js API routes or a thin FastAPI/Node service) on Postgres (managed — Supabase, Neon, or RDS). One relational schema: organizations, users, controls (the fixed 110-control catalog of NIST 800-171 rev2 plus CMMC L2 objectives), control_status, evidence, generated_documents, poam_items, tasks, audit_log. The catalog is reference data the founders curate once, not user-generated — that is a real asset and a real maintenance line.
- Document-ingestion + generation pipeline (THE WEDGE, where complexity lives): file intake (PDF/DOCX/XLSX/Visio) → text/structure extraction (e.g., `unstructured`/`pdfplumber`/`python-docx` + an OCR fallback) → chunk + embed into a vector store (pgvector inside the same Postgres, avoiding a second datastore) → retrieval-augmented prompts that, per control family, draft policy language, populate the SSP template, and emit a control-by-control gap finding with a confidence flag → human-in-the-loop review UI before anything is treated as final. This is an LLM orchestration problem (LangChain/LlamaIndex optional, or hand-rolled), not a model-training problem — the founders are consumers of a hosted model API, not builders of one.
- LLM provider: Anthropic Claude and/or OpenAI via API for drafting and gap analysis. This is a single critical dependency on the generation path (see risks). Embeddings via the same vendor or a smaller open model.
- Async/background: a job queue (a Postgres-backed queue, or a lightweight worker on the host) for ingestion + long generation runs; nothing that requires Kafka or heavy infra at this scale. Renewal/affirmation reminders are simple cron.
- Auth/identity: an off-the-shelf auth provider (Auth0/WorkOS/Clerk/Cognito) with SSO/SAML and enforced MFA from day one — non-negotiable for this buyer. RBAC at the org level.
- Phase 2 integrations (PUNT from MVP): connectors to Microsoft Entra ID/365 (GCC High is the relevant tenant for many DIB customers), Intune/endpoint MDM, and cloud tenants to pull configuration state as evidence. Each integration is OAuth + API mapping + a normalization layer; collectively this is the biggest hidden engineering cost in the whole product and should not be in the first paid release.
- Hosting/data residency: this is the one infra decision that is NOT standard. The customer base handles CUI; many primes/contracts effectively expect supporting systems to live in a FedRAMP-Moderate / DoD-aligned boundary (Azure Government / AWS GovCloud) rather than commercial Vercel+Supabase. This materially changes the stack and cost.

BUILD PLAN TO REVENUE-EARNING MVP

Estimate for one capable full-stack developer, with the second founder on GTM/sales. Total to a Phase-1 product a customer will pay for: roughly 8-12 dev-weeks, with a credible range of 8-16 depending on how much the GovCloud/data-residency decision is forced up front (it can add 2-4 weeks of infra plumbing and procurement friction).

1. Control catalog + data model + auth + multi-tenant skeleton (≈2-3 weeks). Curate the 110 NIST 800-171 controls and CMMC L2 assessment objectives into structured reference data; stand up Postgres, org/user/RBAC, the auth provider with enforced MFA. This is the spine everything hangs on. Cannot be punted.
2. Document ingestion + extraction (≈2 weeks). Upload, parse PDF/DOCX/XLSX, chunk, embed into pgvector. The unglamorous, error-prone part — real customer documents are messy. Cannot be punted; it is the input to the wedge.
3. AI drafting + gap engine (≈3-4 weeks). Per-control retrieval-augmented prompts that draft the policy set + SSP and emit the 110-control gap scorecard + starter POA&M, each finding flagged with a confidence level and citing the source the customer uploaded. Includes the guided-interview logic for the gaps ingestion couldn't fill. This is the differentiated core and the riskiest engineering. Cannot be punted, but scope can be cut to the highest-value document set first (SSP + top control families) and expanded.
4. Human-in-the-loop review + document export (≈1-2 weeks). The editor where the user accepts/edits AI drafts, and clean DOCX/PDF export of the artifacts and the gap report. Cannot be punted — the value proposition is "the artifacts themselves," so output quality is the product.
5. Phase-2 hub (PUNT to v2): continuous evidence collection, IdP/endpoint/cloud integrations, renewal reminders, ongoing control tracking. Ship the first paid release as "get-compliant + a static system of record," sell the renewal/hub as the expansion. The integrations are a multi-month effort and should follow revenue, not precede it.

What earns the first dollar: chunks 1-4 plus the one-time readiness/onboarding package. The annual SaaS renewal value is mostly in Phase 2, so the architecture must be built so Phase 2 bolts on without a rewrite — and it can, because evidence/control_status are already first-class tables.

CRITICAL ASSUMPTIONS

1. "An LLM can reliably read messy contractor docs and draft assessment-grade, control-mapped policy/SSP language and gap findings." This is the bet-the-product assumption. It is plausible today because the control catalog is fixed and finite (110 controls, published assessment objectives), so this is bounded RAG, not open-ended reasoning — but "good enough to pass a C3PAO" is a higher bar than "reads well." Cheap verification: take 3-5 real anonymized DIB document sets, run the pipeline, and have the named CMMC Registered Practitioner / former assessor grade the output against actual assessment objectives. One weekend of advisor time tells you if the wedge holds. [ASSUMED accuracy good enough with heavy human-in-the-loop; without an expert in the loop, do not assume pass-grade output.]
2. "Commercial cloud is acceptable, or GovCloud is a known, bounded cost." If buyers and their primes require the platform itself to sit in a FedRAMP-Moderate-equivalent / Azure Gov boundary because it stores CUI-adjacent compliance data, the cheerful Vercel+Supabase plan is wrong and the real stack is Azure Government / AWS GovCloud with the associated cost, latency, and procurement overhead. Verify before building: ask 5 target customers and 2 C3PAOs, in writing, whether the compliance SaaS storing their SSP/evidence must itself be in a government cloud or FedRAMP-authorized. This single answer can swing infra cost and timeline by 2-4 weeks and ongoing dollars. [ASSUMED commercial-cloud-acceptable for the document-drafting wedge if no live CUI is stored; HIGH uncertainty for the Phase-2 evidence hub.]
3. "We can store the artifacts without storing live CUI." The clean version of this product holds policies, SSPs, gap reports, and pointers to evidence — sensitive but not CUI itself. The moment Phase-2 integrations pull configuration/state, or a customer uploads a document containing actual CUI, the data-classification and handling obligations escalate sharply. Verify by drawing an explicit data-classification boundary in the design and confirming it with the advisor; design the upload flow to detect/refuse CUI in Phase 1.
4. "A single LLM vendor on the critical path is acceptable." Generation quality, price, and rate limits depend on one external model. Verify by abstracting the model behind a thin interface from day one and smoke-testing the same prompts on a second provider; confirm the vendor's data-use/zero-retention terms in writing (important because customer compliance docs flow through the API).
5. "The 110-control catalog and CMMC objectives are stable enough to be reference data." Mostly true post-32-CFR, but NIST 800-171 rev3 and CMMC assessment-guide updates mean the catalog will move. Verify by versioning the control catalog in the schema and budgeting recurring advisor hours to maintain it — this is a permanent maintenance line, not a one-time load.

INFORMATION SECURITY POSTURE

Data collected: customer organizational documents (security policies, network/architecture diagrams, asset inventories, HR/IT procedures, prior assessment reports), generated compliance artifacts (SSP, policy set, POA&M, gap scorecard), uploaded evidence files, and — in Phase 2 — configuration/state pulled from the customer's IdP, endpoint management, and cloud tenants. This is, by construction, a concentrated map of each customer's security weaknesses across a whole book of defense contractors. That is the threat model: Rampart becomes a single repository describing exactly where dozens-to-hundreds of DIB companies are non-compliant and how their networks are shaped — an extremely attractive target for exactly the adversaries CMMC exists to defend against. The security bar here is therefore higher than a generic B2B SaaS, and treating it as anything less is the fastest way to kill the business after launch.

Controls needed at launch (not deferrable): enforced MFA and SSO via the auth provider; encryption in transit (TLS 1.2+) and at rest (per-tenant or KMS-managed keys — AWS KMS/Azure Key Vault, with rotation); strict tenant isolation in the data model with tests proving cross-tenant queries fail; secrets in a managed vault (not env files in the repo), with no long-lived keys in code; immutable, append-only audit logging of every access to documents and evidence (the customer needs this for their own assessment, and you need it for incident response); least-privilege RBAC; and a written, signed data-processing/zero-retention agreement with the LLM vendor so customer compliance content is not retained or trained on. Backups encrypted and tested for restore. A documented incident-response runbook on day one — a breach here is a reportable, contract-threatening event for the customer, so the IR plan is part of the product, not back-office hygiene.

Controls at scale: this product should pursue its OWN SOC 2 Type II early — it is both a sales unlock and table stakes when you are selling "we keep you audit-ready," and it is hypocritical/unsellable to lack it. The founders' stated SOC 2 / HIPAA / GDPR operator background is directly relevant and lowers this risk meaningfully [evidence: prior SOC 2 Type II program experience cited in the one-pager]. If buyers/primes require it, plan for the platform to run inside Azure Government / AWS GovCloud with FedRAMP-Moderate-aligned controls; for some customers the platform's own authorization boundary becomes a buying criterion. PII handling is modest (employee names in HR procedures), but CUI-adjacency is the real sensitivity. Incident readiness, key management, and tenant isolation are the three controls most likely to be tested in a sales security review and must be demonstrably real, not aspirational.

AVERAGE SCORE: 6.7 / 10

TOP 3 TECHNICAL STRENGTHS

- The hard part is bounded, not open-ended: drafting and gap analysis run against a FIXED, finite, published control set (110 NIST 800-171 controls + CMMC L2 objectives), which turns the AI from a risky open-reasoning bet into tractable retrieval-augmented generation over curated reference data.
- Bootstrap-correct build/buy ratio: a paying Phase-1 product is ~8-12 dev-weeks for one developer because auth, database, vector search (pgvector), payments, and the model are all bought; only the ingestion-to-scorecard wedge and review UI are custom (~5-6 weeks of that total).
- Founders' compliance-operator background (SOC 2 Type II, HIPAA/HITECH, GDPR/CCPA) is unusually well-matched to a security/compliance product — they will design the infosec posture and their own SOC 2 from lived experience rather than learning it at customer expense, which is the single most important credibility asset for this buyer.

TOP 3 TECHNICAL RISKS

- Assessment-grade accuracy is unproven: "drafts policy language that reads well" is not the same as "produces an SSP and gap analysis a C3PAO accepts"; if the output needs so much expert rework that the customer still effectively hires a consultant, the wedge collapses.
- Data-residency / GovCloud fork: if buyers or primes require the platform storing their SSP and evidence to itself sit in a FedRAMP-Moderate / Azure Government boundary, the easy commercial-cloud stack is invalid and infra cost, latency, and procurement all rise — an unresolved question that can reshape the build.
- Security blast radius: the product deliberately aggregates a map of where many DIB contractors are non-compliant, making it a prime adversary target; a breach is not just embarrassing but contract-threatening for every customer, so tenant isolation, key management, and incident response must be real at launch, raising the build's front-loaded cost.

BIGGEST SINGLE RISK

The single most dangerous issue is the collision between the product's core value claim and its security obligation: Rampart only works if it becomes the consolidated system of record holding the security policies, network diagrams, gap analyses, and evidence for a book of small defense contractors — which by construction creates the most attractive possible target for the nation-state and criminal adversaries that CMMC was created to defend against, and does so for customers whose entire defense revenue depends on being trusted with CUI. A breach of Rampart would not merely cost the company a customer; it would expose, in one place, exactly where dozens of DIB firms are weakest, and would likely be a reportable, contract-jeopardizing event for each of them — the kind of incident that ends both the vendor and the trust of the niche permanently. This means the security work (multi-tenant isolation proven by test, KMS-backed encryption with key rotation, immutable audit logging, a signed zero-retention agreement with the LLM vendor so compliance content is never retained or trained on, a real incident-response runbook, and very possibly a GovCloud/FedRAMP-aligned hosting boundary) is not Phase-2 hygiene — it is a precondition of selling the first seat, and it front-loads cost and timeline in a way the cheerful "Vanta-but-for-CMMC, ship it on Vercel" framing underestimates. The mitigant is real (the founders have built SOC 2/HIPAA programs before), but the concept must be sold and architected security-first, or the very data concentration that makes it valuable is what kills it.

QUESTIONS THE FOUNDERS MUST ANSWER BEFORE I'M COMFORTABLE

- Does the platform that stores customers' SSPs, gap reports, and evidence have to itself reside in a FedRAMP-Moderate-equivalent / Azure Government or AWS GovCloud boundary to satisfy buyers and their primes — and have you confirmed that in writing with at least 5 target customers and 2 C3PAOs before committing to an infra stack?
- Have you run the ingestion-and-gap pipeline on 3-5 real (anonymized) DIB document sets and had a CMMC Registered Practitioner or former C3PAO assessor grade the AI output against actual assessment objectives, so you know whether "weeks not months" is true or whether the output still needs consultant-level rework?
- What exactly is your data-classification boundary — does Phase 1 deliberately avoid storing live CUI (and does the upload flow detect/refuse it), and at what point do Phase-2 integrations or customer uploads push you into handling actual CUI with the heavier obligations that triggers?
- What are your written terms with the LLM vendor on data retention and model training for customer compliance content flowing through the API, and have you abstracted the model so a price/rate-limit/ToS change does not strand the product on one provider?
- What is your concrete plan and recurring budget to keep the 110-control catalog and prompt mappings current through NIST 800-171 rev3 and future CMMC assessment-guide changes — i.e., who maintains the reference data and how is it versioned in the schema?

RECOMMENDATION: GO (with security-first, scope-disciplined conditions)

The technology is feasible for a two-founder bootstrap, the hard part is genuinely bounded (RAG over a fixed control set, not research), the build to first paid revenue is a realistic ~8-12 dev-weeks for one developer, and the architecture is mostly bought with a thin, defensible custom wedge — all of which clear my technical bar. I am recommending GO rather than REFINE because the open questions are cheaply answerable de-risking experiments, not redesigns, and the founders' SOC 2/HIPAA operator background materially lowers the one dimension I worry about most. The conditions are specific and non-negotiable: (1) resolve the commercial-cloud-vs-GovCloud question in writing with real buyers/C3PAOs before choosing the infra stack, because it can fork the build; (2) validate assessment-grade AI output on real documents with an assessor advisor before claiming "weeks not months," and keep a human-in-the-loop review step as a permanent part of the product, not a temporary crutch; (3) architect security-first — tenant isolation, KMS key management, immutable audit logging, a signed LLM zero-retention agreement, and an incident-response runbook are launch requirements given the data concentration, and the company should pursue its own SOC 2 Type II early as both a sales unlock and a credibility requirement; and (4) punt the Phase-2 integration hub out of the MVP, shipping get-compliant + static system-of-record first and selling the continuous-monitoring hub as the expansion once revenue is in. With those four conditions met, this is a technically sound build whose primary risk is execution discipline on security, not technical possibility.
