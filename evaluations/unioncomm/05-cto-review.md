CTO REVIEW — Member Engagement & Dues-Collection Overlay for Labor Unions

ONE-PARAGRAPH TECHNICAL READ
This is a fundamentally buildable product: it is a CRUD-plus-messaging-plus-payments overlay, all of which is assembled from mature, boring SaaS primitives (Stripe/Plaid for the dues rail, Twilio/Postmark for messaging, Postgres for state, a Next.js app for the front end). There is no ML, no research problem, and no novel infrastructure — the genuine technical complexity lives in exactly two places: (1) the import/sync layer against heterogeneous legacy "databases of record" (Union Link, UnionWare, and a long tail of Access/SQL Server/CSV exports) that are inconsistent, dirty, and frequently on-prem; and (2) running a money-movement and PII rail for a politically sensitive customer that is a high-value target for both data breaches and politically motivated attacks. A two-founder team with prior SOC 2 / HIPAA / GDPR experience and software-dev capability can absolutely ship the wedge; the build risk is modest, but the post-launch operational and security burden of being a regulated-money + sensitive-PII custodian is the part the headline pitch under-weights.

ARCHITECTURE SKETCH
- Frontend: A thin Next.js/React app on Vercel for two surfaces — (a) an admin/leadership console (member lists, hierarchy, campaign composer, dashboards) and (b) a public, mobile-first member-facing renewal/payment microsite reached via a unique tokenized link (no member login required on first touch — that is the conversion unlock).
- Backend: Node/TypeScript (or Python/FastAPI) API on a managed host (Render/Fly/AWS App Runner), Postgres (Supabase or RDS) as the system of engagement. Multi-tenant with strict row-level org scoping mapped to the national → state → district → local hierarchy (a tree/closure-table or materialized-path model — this is the one non-trivial data-model decision).
- Payments: Stripe (cards) + Stripe ACH / Plaid (bank debit) for the dues rail; recurring-billing via Stripe Billing/subscriptions or Stripe-managed recurring PaymentIntents. This is where take-rate revenue lives. Stripe Connect is likely needed so funds settle to each union's own bank account rather than pooling through the founders (critical — see infosec).
- Messaging: Twilio/Telnyx for SMS (with 10DLC/A2P registration per sending org — a real onboarding tax), Postmark/SES for email. Async fan-out of campaigns via a queue (BullMQ/Redis or SQS) and a worker pool; rate-limited send with delivery webhooks for status.
- Integration/sync layer: The hidden-complexity chunk. Connectors/importers for Union Link and UnionWare (likely CSV/Excel export + scheduled re-import rather than live API; many legacy MMS have no usable API), plus a generic mapped-CSV importer with dedupe/merge logic. This is bespoke, dirty, per-customer-shaped work.
- Auth/security: Managed auth (Clerk/Auth0/Supabase Auth) for staff with mandatory MFA and role/hierarchy-scoped RBAC; tokenized one-time links (signed, expiring) for member self-service; secrets in a managed vault; encryption at rest + in transit by default.
- Async/background: campaign send workers, payment-retry/dunning jobs, scheduled re-imports, webhook processors. No exotic infra.
- Where complexity hides: the legacy-data import/dedupe layer, the multi-tenant hierarchy + permissioning, A2P/10DLC SMS deliverability at scale, and PCI/bank-grade handling of money + sensitive affiliation data. The app logic itself is routine.

BUILD PLAN TO REVENUE-EARNING MVP
Estimate: roughly 12–18 weeks of one developer's focused effort to a version that can collect real dues for a first paying local; ~8–10 weeks if scope is brutally cut to a single import path and card-only payments. Chunks in order:
1. Multi-tenant data model + hierarchy + staff auth/RBAC (3–4 weeks). The org tree and row-level scoping are load-bearing; getting them wrong forces a rewrite, so this is not punt-able.
2. Member import + dedupe/merge from CSV/Excel (2–3 weeks). Live Union Link/UnionWare connectors are v2 — ship with mapped-CSV import first; the legacy vendors rarely expose clean APIs anyway.
3. Tokenized renewal/contact-capture microsite + dues payment via Stripe (cards) (3–4 weeks). This is the revenue-earning core. ACH/Plaid and recurring/auto-renew billing can be a fast follow but materially affect take-rate economics, so I would keep recurring card billing in the MVP.
4. SMS/email campaign composer + async send + delivery tracking (3–4 weeks), gated behind A2P 10DLC registration (calendar time, not dev time — start it day one).
5. Basic dashboards (collected dues, contactability rate, renewal conversion) (1–2 weeks) — partly punt-able to v2, but leadership buys on these numbers.
Punt to v2: native legacy-MMS connectors, advanced segmentation/automation, Stripe Connect multi-account settlement polish, granular audit-export, mobile apps.

CRITICAL ASSUMPTIONS
1. "Integrate rather than replace the legacy DB" is cheap. ASSUMED data export is a clean, repeatable CSV/API. Reality: many locals run on-prem UnionWare/Access with no API and gatekept exports. Verify by getting three real (anonymized) member exports from three different prospect locals and timing how long a mapped import + dedupe actually takes — [ASSUMED 1–5 person-days per onboarding local; could be 10+ if data is filthy].
2. SMS deliverability at union scale is frictionless. ASSUMED. Reality: A2P 10DLC registration, carrier filtering of bulk/political-adjacent content, and per-org brand/campaign registration add real onboarding latency and rejection risk. Verify cheaply by registering one Twilio 10DLC campaign now and sending a test blast; measure approval time and deliverability.
3. Members will pay dues directly through a web link at high conversion. ASSUMED 40–70% reachability of those contacted, lower payment-conversion. This is the whole revenue thesis. Verify with one pilot local: run a real renewal campaign and measure contact-capture rate, click rate, and pay rate before generalizing.
4. The freemium-to-monetized motion works because national/state mandates rollout. ASSUMED. Technically irrelevant but commercially load-bearing; verify with a signed pilot from one state body, not a verbal yes.
5. Funds can flow to each union's own bank account (Stripe Connect) rather than the startup holding member money. ASSUMED necessary; verify with Stripe's risk/Connect onboarding for a "political organization / membership dues" MCC, which can trigger enhanced review or rejection — test the account-approval path before writing payment code.

INFORMATION SECURITY POSTURE
The data collected is unusually sensitive for its size: full member rosters, personal cell numbers and emails, payment instruments / bank-debit authorizations, and — implicitly — union membership and affiliation, which is politically and legally sensitive information and an attractive target for both ordinary breach actors and politically motivated adversaries (in a "right-to-work"/paycheck-protection environment, the customer's enemies have motive to obtain or leak rosters). Threat model: account takeover of staff consoles, scraping/enumeration of tokenized member links, payment fraud/chargebacks, insider misuse, and targeted exfiltration of membership lists. Controls needed at LAUNCH (not later): TLS everywhere; encryption at rest; NO storage of raw card/bank numbers — tokenize via Stripe/Plaid so the system is PCI SAQ-A scope; signed, short-expiry, single-use member links with rate limiting and enumeration protection; mandatory MFA and hierarchy-scoped RBAC for staff; full audit logging of who accessed/exported member data; secrets in a managed vault with rotation; least-privilege DB access. At SCALE: SOC 2 Type II (the founders have done SOC 2 before — credible in roughly 1–3 months of process plus an observation window), formal incident-response runbook with breach-notification workflow (US state breach-notification laws apply to this PII), data-retention/deletion policy, and pen testing. The founders' compliance background is a genuine asset here, but the consequence of a roster breach for THIS customer is reputational and physical-safety severe, well beyond a typical SaaS leak — security must be designed in from day one, and it can be with their stack and experience.

AVERAGE SCORE: 6.8 / 10

TOP 3 TECHNICAL STRENGTHS
- Pure-assembly stack with no novel tech: Stripe + Plaid + Twilio + Postgres + Next.js means near-zero research risk and a wedge of only ~4–6 bespoke dev-weeks.
- Founder security/compliance fit is real and material: prior SOC 2 / HIPAA / GDPR work makes a day-one PCI-SAQ-A, MFA, tokenized-link, audit-logged posture genuinely attainable, which matters disproportionately for a politically sensitive PII custodian.
- Clean scaling and a structurally sticky data position: once the product becomes the dues rail and holds the only fresh direct-contact data, switching cost is high and the infra scales 100x on managed services without a rewrite.

TOP 3 TECHNICAL RISKS
- Legacy-data import is the hidden cost center: heterogeneous, often API-less on-prem MMS exports turn "lightweight overlay" into per-customer dirty-data engineering and recurring support load.
- Payments/messaging platform de-platforming risk: a "political organization / union dues" merchant category and political-adjacent SMS content can trigger Stripe risk review and carrier filtering, both on the critical revenue path.
- Breach severity asymmetry: a union-roster leak is a safety/reputational catastrophe for the customer, raising the security bar far above a typical small-SaaS, and any incident could end the business.

BIGGEST SINGLE RISK
The single most dangerous issue is the combination of high-value, politically sensitive data with two third parties (Stripe and the SMS carriers) that can unilaterally cut the service off, sitting directly on the revenue path. The product's entire reason to exist is to be the direct-to-member dues rail and contact channel for unions in hostile legal environments — which means it concentrates, in one startup's database, exactly the membership rosters and payment instruments that the customer's well-resourced opponents have motive to obtain, and it routes all dues through payment and messaging platforms whose acceptable-use and risk teams are notoriously conservative about "political organizations" and bulk political-adjacent texting. A single Stripe risk-review freeze or A2P campaign rejection can halt collections for every customer at once; a single roster breach is not a recoverable "we're sorry" SaaS incident but a potential physical-safety and trust catastrophe that ends the company. The mitigations are concrete and within the founders' competence (Stripe Connect so funds settle to each union's own bank account, pre-cleared MCC and platform-relationship diligence before building, redundant SMS routing, and a designed-in PCI-SAQ-A + tokenized-link + MFA + audit-log security posture from day one), but they must be front-loaded, not deferred — and the platform-dependency piece is partly outside the founders' control no matter how well they engineer.

QUESTIONS THE FOUNDERS MUST ANSWER BEFORE I'M COMFORTABLE
- Have you obtained three real (anonymized) member exports from three different prospect locals and actually run the import + dedupe, to measure true per-local onboarding effort? What is the real number in person-days, and how many distinct legacy systems must you support?
- Have you confirmed with Stripe (or an alternative like a union-friendly processor) that "labor union / political membership dues" is an approved merchant category, and will you settle via Stripe Connect to each union's own account so you never hold or co-mingle member funds?
- Have you registered an A2P 10DLC campaign and sent a real test blast to measure approval time and deliverability for union/political-adjacent content, since carrier filtering directly threatens the messaging channel?
- What is your incident-response and breach-notification plan for a union-roster leak, given the elevated physical-safety and political stakes, and who is accountable for it on a two-person team?
- In your pilot, what were the measured contact-capture rate, link click-through, and direct-pay conversion — the three numbers the entire take-rate revenue model depends on?

RECOMMENDATION: REFINE
The technology is sound and well-suited to a bootstrapped two-founder build — boring stack, thin custom wedge, ~12–18 dev-weeks to real revenue, and a founder skill set that genuinely covers the security bar this customer demands. It is not a GO yet because three de-risking experiments must precede serious building: (1) run real legacy-data imports from multiple prospect locals to size the dirty-data tax and decide which systems to support; (2) get explicit Stripe/processor merchant-category clearance and design Stripe Connect settlement so you never hold member funds; and (3) register and test an A2P 10DLC campaign to confirm political-adjacent SMS deliverability. Scope cuts for the MVP: ship CSV/mapped import only (defer native Union Link/UnionWare connectors), card + recurring billing first (ACH/Plaid as fast follow), and basic dashboards. If the import effort proves bounded and Stripe/carrier paths clear, this converts cleanly to GO.
